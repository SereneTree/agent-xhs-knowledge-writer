# 技术与图文复核

## 证据优先级

先定位原始论文、官方文档、官方源码/测试/发布说明；确认语言、包版本、API路径和获取日期。主题不需要最新版本时也不要引用旧默认值为通用定律。第三方教程和用户样例用于找问题，不自动视为正确答案。

网站内容默认 Browser Use 获取；官方可下载文件与用户明确要求的 API 路径按宿主授权使用。闭源行为无法验证时写清条件与未知。不调用不存在的工具，引用格式遵循交付技能规范。

建立 claim ledger：每条重要主张记录 `claim / source_url / source_section / version / evidence_type / limitation / verification`。正文在对应结论处引用，不能只在文末堆链接。小红书稿保留可读的来源说明，详细出处保存在教材。

## 反例审查

逐条审问“必须/只能/全都/必然/显著/唯一/默认”：它是定义、配置、经验建议，还是带条件的实验结论？找得到例外就改成有边界的表述。不给无来源的普遍比例、工期、热度和企业面试偏好。

需主动防止本系列曾出现的误区，**下列是复核提示，不是替代官方核验的知识库**：
- 不把 Tool-use、RAG、ReAct、框架、产品平台放在同一个互斥分类；不把多节点等同多 Agent。
- 不把工具十个、压缩八成、检索权重一半等写成铁律；阈值须来自明确版本或实验设定。
- 多环节成功率相乘须说明“各环节全成功才算成功”，及独立概率或条件概率的口径。Agent 数不等于关键串行步骤数；冗余、纠错、相关错误会改变模型，不能无条件用 0.95^N 算所有多 Agent 系统。
- “无统计显著提升”不等于已证明负收益；看样本量、区间、功效及成本/时延/安全收益，结论可为证据不足。
- 重试是分层策略；执行器可做局部瞬时重试，编排层管全局预算与替代方案，避免叠加重试风暴。幂等键绑定一次业务意图，不能只用相同参数哈希使两次合法新请求被误去重。
- 超时不证明未执行；状态查询未查到也可能最终一致性延迟。`sync` checkpoint、拆节点或把操作放在 interrupt 后，不自动保证外部副作用 exactly-once。
- 同 id 的 `add_messages` 可更新消息，不等于所有重放都有自动去重；重新生成的 id 仍会产生新消息。条件边不必限于 N 选1；子图步数、并行 pending writes、恢复行为必须针对版本验证。
- Memory 不是只能存个人偏好；共享经验、程序性记忆、任务状态也可成立。少量高优先级偏好可按需预加载，不应宣称全部语义记忆无条件进 system。
- RAG 语料不天然可信，知识检索可实时触发；Memory 可复用 RAG 机制。摘要追加也会积累错误，不是天然无损。工作过程可压缩/外置，但结论、证据、未决状态、权限不能无条件丢弃。
- Reflection 是模式；Self-Refine/Reflexion 是具体方法，比较需回到原论文。模型评审与外部验证均有误差；测试通过只覆盖测试范围。不要承诺反思必然收敛或必须使用完全非 LLM 验证器。
- 代码工具、沙箱、MCP/A2A、框架不构成天然安全边界；权限、网络、文件和数据范围由系统实际约束。

## 代码与公式检查

完整示例：明确 Python 或 JavaScript/TypeScript，列出依赖与版本、imports、初始化、运行入口、测试输入和期望行为。运行正常、边界与失败例子；区分离线 mock、真实模型、真实外部服务验证。不要写“可直接运行”却包含未定义函数。

局部片段：标“机制示意/伪代码”，说明省略项。秘密走环境或可信注入；schema里的用户输入不承担鉴权。不要打印敏感材料或把 trace 明细全部交付。

所有算式由工具复算；指标定义分子分母、数据来源与测量条件。时间衰减的 half-life 参数不要误写成普通 e-folding 时间常数。

## 图的语义先于排版

先保存 diagram manifest（题目、对应教材版本、nodes、edges、图例、路径检查），再渲染。每条连线必须能翻译成清楚的句子，区分控制流、数据流、读写、依赖和装饰。

逐项核对：
1. 概念层级与分组是否正确，箭头是否误把分类画成必经流程。
2. 主链是否从输入到输出完整，分支条件是否完备且不互相矛盾；没有依据的重试/回退线不添加。
3. 并行任务的 fan-out/fan-in、依赖顺序、聚合门是否明确；失败后重試应回到执行/等待状态，不能直接指向“成功聚合”。
4. 终止、失败、超时、人工确认以及预算耗尽路径是否按本图范围表达；简化省略项在图注中交代。
5. 标签、状态、数字、模型/框架名与正文、代码一致；正常路径不能被画成必经失败决策；停止节点不能默认向成功答案连线。

使用 `check_content.py diagram` 只检查 ID、引用、孤点、不可达、分支标签等基础结构。封面另存 cover manifest，`check_content.py cover` 强制封面单元 1—2 个、canvas 为竖版 3:4、双页 core_points 带 page 标注，且 core_points 全集覆盖教材核心章节与压缩正文（含失败分支或 NA 理由）；审阅者必须另外逐点逐页逐边走读正常和失败案例，检查概念含义，字段齐不等于语义覆盖完整。

## 渲染后检查

以读者能打开的最终图为对象，检查中文字体、箭头起止、压线压字、裁切、空白、边距。保持源文本清单，与 OCR/人工读图逐项对照；OCR不替代人眼判断。将封面缩到手机阅读宽度查看，不靠放大才读懂主问题。

## 云文档回读证据（不是布尔通过）

发布模块前置进同一份云文档后，必须实际回读并把门证据写进 doc-snapshot.json：两个模块正文各导出 body_file，摘出前置发布模块与教材模块，逐内容/hash 对照本地 post.txt 与 textbook.txt；确认前置位置正确、同一 URL、doc 版号非空、教材模块完整保留在后。脚本实读 body_file 算 hash，不只信声明字符串。叙述性说明写进 review.md。只凭“review 已勾选”这类布尔标记不算云端检查。本地脚本只能证明本地附件一致，不得在记录或回复里声称已验证真实飞书内容；云端核对结论以实际回读为准，回读不到就如实标未验证。

检查完成的 review.md 包含：版本、核验过的范围/来源、代码验证环境和结果、图的路径测试、修复、仍未验证项。没有独立审阅者就如实标同一执行者复核。交付有界结论，不写“所有内容绝对正确”。

## 停止条件

有改变核心结论的未决问题、关键代码失败、图文不一致或图不可读时，先修复；必要时向用户说明阻塞，不请求用户“通过”未完成稿。非关键缺口可以明确标注后交付带未覆盖项说明的教材草稿，但停止后续阶段直至质量问题修复；不得在公开稿抹掉缺口。
