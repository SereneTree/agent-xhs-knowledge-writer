# AI 新闻与行业解读·类别规则

本文件是技能内与「技术机制／面试拆解」并行的第二内容类别规范。技术类四阶段（A 思路 → B 教材 → C 发布正文 → D 封面）及其字数门、封面门、固定结尾、stage_gate 状态机只适用于技术类，不向新闻类外推；技术类既有模板保持不变。

## 定位与口吻

- 角色是行业观察者：解释事件的机制含义与行业影响，不做快讯搬运、不做情绪煽动。
- 服务既有读者画像（计算机专业本科与研究生、Agent 方向求职群体），帮他们建立对行业事件的技术判断力。
- 不强行转写成面试题；确有面试关联时，最多在「接下来值得观察什么」里点一句，不把新闻稿改成面试讲稿。
- 技术机制只在解释新闻所必需时最小引入：用读者能懂的一层机制讲清即可，不展开教材式推导，不堆代码。

## 四段结构（固定骨架）

1. **发生了什么**：事件本身，主体、动作、时间、信息来源。
2. **为什么重要**：事件在技术、产品或行业链条上的含义，回答 “so what”。
3. **对谁有什么影响**：至少落到一类具体对象（开发者、求职学生、企业客户、同行厂商、监管者等），不写“对所有人影响深远”式空话。
4. **接下来值得观察什么**：可验证的后续信号（产品发布、规则落地、数据披露、竞争动作），不是愿望清单。

## 事实分级（每篇必须显式标注）

- **已证实**：官方公告、监管文件、公司一手渠道可核验的事实，注明来源与核验时间。
- **媒体报道**：媒体援引知情人士或二手转述、未经官方确认的信息，保留“据……报道”措辞，不升级为确定表述。
- **分析判断**：作者基于事实的推断与观点，判断句与事实句显式分开，不把推测写成事实。
- 时间敏感事实（融资、上市进程、产品发布、政策状态等）必须注明核验时间（精确到日期）；状态可能变化的，写“截至 YYYY-MM-DD 核验”，不写无依据的完成时断言。
- 不同来源信息冲突时，以一手渠道为准并显式说明冲突，不静默选边。

## 禁止事项

- **不做新闻搬运**：只转述事件、没有解释增量的选题不成立。
- **不过度预测**：不写无证据的时间表、市场份额断言或确定性结局；预测必须给出依据与不确定性。
- **不做投资建议**：不荐股、不评判估值高低、不写买入/卖出/目标价类内容；商业成功不等同技术优越，公司经营表现不作为技术能力的证据。
- 不编造来源、数据或引语；拿不到一手来源时降级表述或不写。

## 与技术类流程的边界

- 不机械套用长教材（5000—10000 字）、发布正文严格 1500 字门、面试追问、技术类固定段落与固定结尾句「关于XXX相关问题，欢迎一起交流～」、求职标签结构、技术类手绘封面流程、cover manifest/cover-review 登记与 stage_gate 状态机登记。
- 交付形态（单篇文稿、图文、云文档等）与篇幅在思路阶段按用户当次要求确定；用户未指定时，在思路中给出建议并说明理由，不默认套用技术类「教材 + 发布正文 + 封面」三件套；用户当次明确要求配图时可交付可选图文，但不套用技术类封面单元/manifest/字体门与登记。
- 事实核验质量门不取消：来源分级、核验时间、冲突处理必须执行，只是不登记技术类 tb-review / cover-review 证据结构。
- 不做发布、私信、评论、关注等账号动作，与技术类边界一致。

## 发布节奏

- 不预设固定频率或新闻类占比。是否小比例试发、何时发，由用户逐次决定；建议性节奏不写成技能规则。

## 思路阶段最低对齐项

新闻类先在对话内展示思路，至少覆盖：选题与新闻由头；四段各自的要点；事实分级清单（每条信息归哪一级、来源与核验时间）；需要最小引入的技术机制；明确不写的内容（未证实信息、无依据预测、投资建议）。
