# 写作规范与分层讲解

## 读者与账号

主读者是 **AI Agent 方向校招/实习面试的计算机专业本科生与研究生**：含研三、博三、应届硕士，也覆盖更早阶段准备面试的本科/硕士在读生，目标以开发岗为主（后端/算法/AIGC 应用）。他们多数读过 LangChain 文档、看过几篇论文、跑过 demo，但普遍没做过线上系统、没调过生产参数、没踩过真实故障——写作时不要假设人人都有生产项目经历。

每篇确定一个主读者，不在一篇里分别写四份教程。产品/运营/解决方案岗只在”需要理解 Agent 能力边界”时一笔带过，不单独写教程。用同一案例说明其他岗位需要理解的决策。

专业来自准确的概念、可解释的机制、可验证的判断，不来自”内幕””必过””面试官一听就加分”。不虚构作者是大厂面试官或亲自操盘过某项目。通用示例明确叫”教学案例”，不能用”我们线上提升了…”描述假数据。

**内容重点是”面试时怎么把机制讲清楚”**：给具体参数值和理由（温度设多少、context window 怎么切、重试几次）、给具体失败案例（什么现象、怎么定位、怎么修，用教学案例/可复现示例说明，不冒充线上亲历）、给具体选型理由（什么场景选 A、什么场景选 B、为什么）。必要前置与机制深度不砍，用例子辅助理解；既不堆术语装晦涩，也不把专业内容降成纯大白话。学生能举反例和推导过程，比背固定默认值重要。

## 篇幅口径

- 思路：**完全不设字数限制**，在对话先交付，不跑字数检查。讲清方向和取舍优先，宁详不简——思路是唯一一次纯人工对齐的机会，这里省下的字后面要用整篇教材返工来补。
- 教材：正文默认 5000—10000 字，**以把面试问题讲清楚为目标，不为凑字数扩写、不默认追求上限**。低于 5000 说明覆盖不足，应补讲机制、反例或参数取舍，而不是放水通过。确需超过 10000 字时，必须随 `check_content.py count … --over-reason` 给一句非空理由，并在 `review.md` 写明哪些核实过的数据、机制说明或必要反例不可删——这不是一律拒绝，也不是默认顶格；只为回到区间而删掉数字、来源标注、机制解释或反例会直接降低教材可用性，真正该删的只有重复表述和与主线无关的旁支。代码是辅助，只在直接相关处少量配合说明，不能用成百行代码冲字数，也不为篇幅堆大量实现细节。
- **小红书发布稿默认形态是：1—2 张竖版 3:4 手绘封面（默认 1 张；单图密度不可读时并列分块为 2 张）+ 900—1100 字完整发布正文**（非空白可见字符，以 `check_content.py count … --stage post` 实测）。不是图卡合集、不是 100—200 字引导语。封面要求见下文「发布稿形态」与 `cover-style.md`；正文写法见「发布正文写法」。
- 统一按”非空白可见字符”统计，标点、数字、英文字母逐字符计；Markdown语法标记与链接地址不计，链接文字计入。
- 发布稿标题、标签、参考来源、封面文案另存，不计正文。
- 教材正文另存纯文本；来源清单、目录、代码块另存或在统计时剔除。脚本同时给中文字符数、英文词数、去空白字符数，向用户说明主口径。不以 token 数代替字数。
- 用户指定另一口径时重新标记并统一重算，禁止半途换口径凑达标。

## 思路阶段的内容（不限字数，直接在对话里给）

思路要让用户能在动笔前就判断方向对不对、章节该不该调、案例合不合适。**宁详不简**：这里多花的字，省的是整篇教材的返工。可分小节展开，但不直接写成教材正文。

**交付方式：思路全文直接写在对话回复里，不写成 txt、不建文档、不用 `present_files` 交付。**思路在对话里展示即完成对齐；按自动策略登记后不停顿，直接继续教材。落盘只为流程登记需要（`stage_gate.py record --stage outline` 要一个文件路径），登记用的文件不作为交付物呈现给用户，也不在回复里报它的路径。教材和发布稿另有交付要求，不受这条影响。

### 必须覆盖的部分

1. **读者与前置**：主读者是谁、兼顾哪些岗位、为什么这些岗位能用同一套内容覆盖；读者需要预先懂什么、不需要懂什么。
2. **这篇要回答的具体问题**：以及读者当前最常见的错误理解或翻车方式。写具体错法，不写"理解不深"。
3. **核心判断**：一句话能复述的主张，必须是有信息量的判断，不是"很重要""是关键"。
4. **章节推进及其理由**：逐节说明这节讲什么、为什么排在这个位置、上一节没有它会缺什么。**每节要点出具体内容**——具体数字、具体机制、具体反例，而不只是章节名。这部分是思路的主体，占篇幅最多。
5. **贯穿案例**：案例是什么、为什么选它、读者能怎样自己验证机制、正常路径和故障路径各对应什么。
6. **已核实与待核实**：已读了哪些一手来源、拿到哪些关键数字；还有哪些数字是二手转引、必须回原文，以及找不到时的处理方式（不写进正文 / 标注限制）。
7. **教材与发布稿分工**：教材会额外沉淀什么（代码、schema、完整数据、不适用场景），发布稿只保留哪条主线。
8. **封面主结构**：画什么关系、为什么这个关系最该被记住。
9. **表达边界**：有无真实面试来源、数据口径怎么标、哪些承诺不写。

### 写法要求

- **每节的要点要写出实质内容**。写"第二步讲渐进式披露，Level 1 约 100 tokens 始终加载、Level 2 命中才读且 5k 以内、Level 3 按需读无上限，关键是脚本代码从不进上下文只有输出进"，不写"第二步讲渐进式披露机制"。用户要靠这些判断你有没有真读懂。
- **点出你打算纠正的具体错误说法**，包括它出现在哪类来源里、为什么错、照抄会被怎么追问。
- **写明你做过的取舍**：为什么不按教科书顺序、为什么某个内容放教材不放发布稿、为什么砍掉某个看似相关的话题。
- 末尾不再等确认；登记思路后自动开始教材。没有题目时只问题目，不替用户默认选题。

## 按主题搭论证

### 宏观：架构、范式、技术版图

先定义问题与约束，再讲最小闭环。沿“单体遇到的失败→可以增加什么机制→增加后有什么成本→如何检验收益”推进。分类必须标维度，架构、框架、SDK、协议、平台不能混成一排互斥选项。

### 中观：Tools、Memory、RAG、LangChain/LangGraph等

先说明组件在整个 Agent 中的位置与输入输出；沿一次真实调用顺序讲机制，然后落到数据结构、状态变更、异常与评测。首次术语给“准确名词＋一句解释”，后文直接用术语。

### 微观：一个面试题或具体工程问题

问题→简明答案→为什么→最小例子→边界/反例→追问及完整答复。题目里缺业务条件时显式说明假设；不能把演示 API 当成通用保证。

## 教材最低内容覆盖

不是固定章数，按自然推导组织：
- 读者前置、要解决的问题、术语定义和系统位置。
- 完整机制、输入输出、状态/控制/数据流；必要示意图。
- 至少一个贯穿教学案例：正常路径与一个故障路径；有工程实现需求时给代码/schema及解释。
- 适用/不适用、替代方案、资源成本、异常恢复、安全与权限。
- 可测的成功标准、失败归因、改进方法；每个提出的面试问题都要回答。

不要为了自学教材用面试官打分口吻训人；不写”不知道这个就可以结束面试””只有踩坑过才知道”。学生能举反例和推导过程，比背固定默认值重要。

## 发布稿形态（默认）

小红书发布稿 = **1—2 张竖版 3:4 手绘封面（默认 1 张）+ 900—1100 字完整发布正文**。不做知识图卡轮播，也不写 100—200 字引导语。封面承担"一眼看完答题骨架"，正文承担"把面试问题讲清楚"。

### 封面要求（1—2 个单元：默认一张，密度过高时两张并列分块）

- 每个封面单元都是竖版 3:4（宽:高=3:4，参考 1080×1440）；顶部主问题；中间按 diagram_type 展开：flow 画输入到输出的完整控制链路（含关键失败分支：哪一步断、重试/降级/中止各走哪条路），structure 画模块分区与关系，mixed 主干流程加框架分区；底部一句适用边界。学生光看封面集合（单页看一页，双页按 ①→② 看两页）能复述完整答案。
- 手绘规范（米白纸纹、手绘框线、Purisa 英文 / Noto Sans CJK SC 中文、竖版 3:4 尺寸）见 `cover-style.md`。
- 数量规则：默认 1 个单元；单页提炼层次后仍密度不可读（字号过小、节点重叠、连线交叉）时才拆 2 页并列分块，无总览页、两页合起来覆盖全集；0 个或 ≥3 个拒绝。拆分理由与两页分工写入 review.md。
- 结构存 cover manifest 并用 `check_content.py cover` 校验：封面单元数量必须在 1—2；`canvas` 必填且为竖版 3:4；双页时每个 core_point 标注 `page`（0/1）；core_points 从教材核心章节+压缩正文提炼，problem/judgment/module/mechanism 必备，failure/tradeoff/boundary 缺项须写 coverage_na 理由；source_sections 每章要么有 core_point 要么有排除理由；flow 类须有带两条标注控制边的 decision（或失败确不适用的 NA 理由）。

### 正文（900—1100 字）

- 正文本身就是完整短文：核心判断前置 → 一次真实调用流程 → 失败与边界 → 关键参数取值与理由 → 选型对比。不写成"干货在图里"的导语。
- 执行口径：`check_content.py count post.txt --stage post` 落在 900—1100（非空白可见字符）。低于 900 说明讲得不透，应补机制或反例；高于 1100 回内容层删旁支，不删判断、解释和例子。

### 标签

固定 8—10 个，**求职场景标签占 60%，技术标签占 40%**：
- 求职场景：#校招 #秋招 #面试经验 #大厂实习 #求职辅导 #程序员（按选题选 5—6 个）
- 技术标签：#agent #LangChain #AI面试 #大模型 等（按选题选 3—4 个）

标签写在发布稿文档末尾单行或交付回复里，不单独成节。

## 发布正文写法（默认形态的正文要求）

以下排版与写法规则适用于默认形态的 900—1100 字发布正文，不是备选模式。

首段直接接题并给总判断，不用“随着AI发展”。按核心机制递进成4—5个可扫读段落组：每组有新信息并衔接上段，不能只是知识点堆列。

必须留下：核心定义、关键运行链、至少一个小例子、适用边界/代价、验证或排查方法。微观题优先讲透一个机制，宏观题控制选型范围，不把教材所有 API 压成名词串。

第一次出现的关键术语括注即可，例如“幂等（重试同一次业务操作不会重复生效）”。不用每个普通英文都长篇解释；用户另要通俗备注时附独立注释版，不混入发布稿字数。

保留专业词但用中文句法；不把整句硬翻成英文。段落长短由逻辑决定，不强行“三条原则”“五大核心”。不写泛泛行动建议、读完就会、必考、大厂最爱等未经证实的承诺。

### 小红书阅读形态（与长文档写法的关键差异）

小红书在手机上竖屏滑动阅读，读者先扫后读。同样的信息量，排版决定它是被读完还是被划走。以下按实际发布反馈沉淀，优先级高于“书面段落更完整”的直觉。

- **可枚举内容必须逐条拆开，一条一行**：环节、控制点、形态、代价、原则这类本就成列的内容，写成 `1️⃣2️⃣3️⃣` 独立短行，不要合并成叙述段。合并会让读者在滑动中失去计数感，也无法回扫定位。
- **用 emoji 承担序号与判定**：`1️⃣`—`5️⃣` 做枚举，`✅`/`❌` 做正反判定。这是平台阅读习惯，不算装饰性 emoji，与“正文不滥用 emoji”不冲突；但不要给普通段落或标题随意加表情。
- **章节标题独立成行并编号**：一、二、三……每节一个明确主题。标题可直接写结论，如“三、四环节：生成、评判、决策、重写”，让扫读者只看标题就拿到骨架。
- **例子后置、结论前置**：先给判断，再补例子。教材可以“铺垫—推导—结论”，发布稿必须倒过来。
- **段间留空行**：宁可多几个空段，也不要出现连续五行以上的密集文字块。

### 每个枚举条目要自带解释，不要只留标签

以下几条是按用户实际手改稿沉淀的，纠正“越短越好”的过度压缩倾向。压缩的对象是旁支和重复，不是论证本身。

- **条目 = 标签行 + 解释行**：`1️⃣2️⃣3️⃣` 那一行给判断或名称，紧跟一到三句说明它是什么、为什么这么做、做错会怎样。只有并列短项（如五类失败的名称本身、一组触发条件）才允许单行不带解释。
- **枚举条目可以长**：一条写到三四行是正常的，前提是每行都在推进论证。不要为了“每条两行以内”把机制说明砍成名词。
- **判定符号后面要接理由**：`✅`/`❌` 不是结论标签，而是对照的开头。`❌ 标在第 13 步` 后面要说清它会导出什么错误结论、进而误改什么。
- **`✅` 条目的主语要完整**：写 `✅ F3 参数问题 → 要上 schema 校验`，不写 `✅ F3 → schema 校验`。读者是扫读进来的，不保证记得 F3 指什么。
- **术语给中英文对照**：关键概念首次出现时括注英文或读法，如“首次偏离点（first deviation）”“pass^k（读作 pass hat k）”。学生要靠这个去搜原文。
- **给出可执行的具体值**：涉及配置的地方写清取值与理由，如“Agent 侧温度设 0，有用户模拟器时设 1 以制造合理的表述差异”，不写“温度要固定”。
- **补一条“怎么长期用”**：讲评测、监控、复盘类主题时，除了怎么搭还要说怎么维护——看什么指标的变化、什么信号说明该回头审方法本身。这类内容学生最缺，也最能体现作者真做过。

### 章节标题写成判断句

标题是扫读者唯一一定会读的部分。只写对象名会浪费这个位置。

- 写 `三、要看首次偏离点：归因唯一可靠的锚`，不写 `三、标首次偏离点`。
- 写 `五、区分稳定错与抖动错`，不写 `五、跑一次什么都说明不了`——后者是现象，前者是读者要学会的动作。
- 结构是「动作或对象 + 冒号 + 为什么重要」，或直接写成读者要做的判断。

### 用飞书原生结构而非纯段落

发布稿在飞书文档里交付，读者也可能直接在文档里读。同层级的并列项用 `<ul><li>`，不要连续堆 `<p>`。关键判断用 `<b>` 加粗——每节一到三处，落在“这一节读者必须带走的那句话”上，不要整段加粗。章节标题用 `h1`，让飞书大纲能直接当目录用；发布稿正文层级浅，不需要 `h2` 再分层。

### 发布正文字数口径

正文统一按 900—1100 非空白可见字符执行（`check_content.py count post.txt --stage post`）。排版带来的拆行、编号、判定符号、解释行属于可读性收益，在区间内自然吸收，不再设"骨架—成稿"两步放大口径。

执行口径：
- 先把内容写到 900—1100 区间内，再做小红书形态排版并给每个枚举条目补解释；
- 低于 900 说明讲得不透，补机制、反例或参数取舍，不凑字；
- 高于 1100 回内容层删旁支或减章节，而不是把已拆开的条目合并回段落、或把解释行删成裸标签。

**判断依据是"每一行是否都在推进论证"，不是字符数。** 宁可 1050 字每条都讲透，不要 900 字留一堆读者看不懂的标签。

### 结尾

最多一句咨询入口，可再加一句轻量互动（如“欢迎多交流”），不叠加多个 CTA。口气平实，不写“来做一次诊断”这类服务感过强的表述，用“可以带着目标岗位和项目经历聊一次”即可。


## 标题与转化

沿用用户拟定题目：“大厂面试总结：XXX”“大厂面试问：XXX”。不擅加具体公司或高级职级；没有该公司来源时，正文首次交代模拟题属性。若用户要标题优化，提供少量不夸大的替换，不强改固定系列名称。

默认结尾最多一句咨询入口，如“如果卡在项目怎么讲，可以带着目标岗位和项目经历做一次诊断。”只在确有服务/资料时提及，不编价格、名额、客户证言、offer数量，不宣称官方背书。正文须已提供完整可用信息，不能故意挖空答案逼付费。

教材不夹营销；发布稿最多一个 CTA，标签按上文「标签」节固定 8—10 个单列（求职场景 60% / 技术 40%）。实际发布/外链导流规则不凭旧印象推断，涉及平台操作时重新核验，未经授权不发布。

## 云文档的交付结构（教材 + 前置发布模块，同一份文档）

发布正文与完整教材在**同一份飞书云文档**里，不另建发布文档：

1. 文档标题（题目）
2. **前置发布模块**：发布正文，章节用 `h1`。封面由 D 独立交付（可编辑源 + 预览），不强制插入云文档，避免变成不可变封面的硬规则。
3. **教材模块完整保留在后**：不覆盖、不删节、不与发布模块混排

**不要加的东西**：字数/校验状态/教材版本对应关系这类元信息表格、放在文档里的数据来源清单。这些属于叙述性复核记录，写进本地 `review.md`（含必要超长时不可删的数据/机制/反例清单），不进云文档。标签写在交付回复里或文档末尾单行，不单独立节。

原因：作者从前置模块全选复制去发，中间夹的表格和来源节都要手动删掉；教材留在后面供追问与追溯。

来源可信度仍要保证——数值和结论必须能在教材里追溯到出处，只是出处清单不放在发布模块里。发布模块前置后云文档版本号自然变化，与教材内容 sha256 分别记录；回读时摘出前置模块与教材模块逐内容/hash 对照本地文件，确认前置位置、同一 URL、教材完整。
